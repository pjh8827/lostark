문제 해결 상세

Problem 1
로그 분석 결과 트랜잭션 범위가 불필요하게 넓어 DB 락을 과도하게 유지. 일부 외부 API 호출까지 트랜잭션 내에 포함되어 락 지속 시간 증가.
Solution
데이터 정합성이 실제로 필요한 구간에만 트랜잭션을 명확히 적용하도록 재설계. 외부 I/O를 트랜잭션 밖으로 분리. 성능 테스트 직접 주도해 검증.
Result
평균 API 응답 시간 3,000ms → 100ms (97% 개선). DB 락 경합 감소로 동시 요청 처리 안정성 향상.
Problem 2
전자결재 도메인은 역할·문서 상태·조직 관계에 따라 행위별 권한이 복잡하게 달라짐. 기존 코드는 권한 로직이 각 API마다 중복 구현되어 보안 리스크 누적.
Solution
인증은 공통 필터, 인가는 도메인 서비스 레벨에서 중앙화. 권한 로직을 한 곳에서 관리해 신규 API 추가 시 중복 구현 불필요.
Result
보안 리스크 감소, 개발 효율 향상. 신규 API에 인가 로직을 재사용하는 구조로 유지보수 비용 절감.
Problem 3
MSA 전환 중 네트워크 단절 시 처리 실패 이벤트를 수동으로 재처리하는 작업이 월 수십 건 반복. 운영 부담 및 데이터 정합성 위협.
Solution
Kafka로 모든 처리 이벤트를 기록하고, 네트워크 정상화 시 배치가 자동 재처리하는 구조 설계·구현. 장애 시에도 데이터 유실이 없는 멱등성 보장 구조 확보.
Result
수동 복구 작업 월 수십 건 → 0건. 운영 개입 없이 데이터 정합성이 자동 유지되는 안정적인 구조 확보.

Spring 병렬 처리 최적화

// sterm 기준값 추출 → 나머지 14페이지 URL 선계산 후 동시 요청
long stermBase = Long.parseLong(firstSterm);
List<CompletableFuture<Document>> pageFutures = IntStream.range(1, maxIterations)
    .mapToObj(i -> {
        long sterm = stermBase + (long)(i - 1) * 10_000L;
        return CompletableFuture.supplyAsync(
            () -> fetchDocument(url + "&sterm=" + sterm), PAGE_EXECUTOR);
    }).collect(Collectors.toList());
// 게시글 본문 확인 — POST_EXECUTOR(10), 부캐 검색 — CHAR_EXECUTOR(6)
